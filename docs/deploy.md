# Deploying the live demo

The API and database run on Render. The web app runs on Vercel. Nothing here is automated beyond the two config files, so each step is a click in a dashboard.

| Piece | Host | Config |
|---|---|---|
| Postgres 16 | Render (free) | `render.yaml` |
| FastAPI | Render (Docker, 1 instance) | `render.yaml` |
| Next.js | Vercel | dashboard settings below |

## 1. API and database on Render
1. Push the repo to GitHub.
2. In Render choose **New → Blueprint** and select the repo. Render reads `render.yaml` and proposes `credisure-db` and `credisure-api`.
3. When prompted for `CORS_ORIGINS`, enter the web origin(s) as a comma-separated list, with no trailing slash and no spaces needed, for example `https://credisure-ops.vercel.app`. You can add the preview URL too: `https://credisure-ops.vercel.app,https://credisure-ops-git-main-yourname.vercel.app`. If you don't know the Vercel URL yet, put a placeholder and edit it after step 2.
4. Apply the Blueprint. On first start the container runs `alembic upgrade head`, seeds the fictional data (skipped when staff already exist), and starts `uvicorn` with one worker.
5. Open `https://credisure-api.onrender.com/health`. It should return `{"status":"ok", …}`. If Render gave the service a different name suffix, use that URL everywhere below.

Notes:
- `DATABASE_URL` comes from the database. Render supplies a `postgres://` URL and the API rewrites it to `postgresql+psycopg://` (`app/core/config.py`).
- `JWT_SECRET` is generated by Render. No secret is stored in the repo.
- `PORT=8000` makes Render route to the port the container image listens on.

## 2. Web on Vercel
1. **Add New → Project**, import the same GitHub repo.
2. Set **Root Directory** to `web`. The framework is detected as Next.js. `output: "standalone"` in `next.config.ts` is fine on Vercel.
3. Add the environment variable `NEXT_PUBLIC_API_URL=https://credisure-api.onrender.com` (no trailing slash) for Production and Preview.
4. Deploy. Copy the production URL.
5. Go back to Render, open `credisure-api → Environment`, and set `CORS_ORIGINS` to the production URL (add the preview URL after a comma if you want previews to work). Save; Render redeploys.

`NEXT_PUBLIC_API_URL` is baked in at build time, so changing it needs a redeploy of the web app.

## 3. Cold starts
The free API sleeps after 15 minutes without traffic. The first request can take about 50 seconds. While it wakes, the header health dot shows "Checking…" and then recovers; the login button may need a second try. Open the site a minute before a demo.

The simulated provider mode lives in API memory (ADR-005), so a restart resets every provider to Up.

## 4. Smoke-test checklist for the live URL
- [ ] `https://<api>/health` returns ok and `https://<api>/docs` loads.
- [ ] Sign in as `admin@credisure.demo`. The header dot goes green.
- [ ] Overview shows four stat cards, the funnel, the needs-attention list, the chart and provider health.
- [ ] Businesses: filter to "Checks in progress" and "BVN failed". Copy the URL, open it in a new tab: same view.
- [ ] Open a failed business, re-run the check once. A toast appears and one audit entry is added.
- [ ] Providers: set BVN to Down. The banner appears and the header dot turns amber. Set it back to Up.
- [ ] Sign in as `viewer@credisure.demo`: only Overview and Providers in the nav, no simulate control.
- [ ] Phone width (or a real phone): the hamburger menu opens, navigates and closes.
- [ ] No CORS errors in the browser console.

## 5. Troubleshooting
| Symptom | Likely cause |
|---|---|
| Login says it can't reach the API | `NEXT_PUBLIC_API_URL` wrong or the API is still waking up |
| Console shows a CORS error | `CORS_ORIGINS` doesn't include the exact web origin (scheme and host, no trailing slash) |
| API crashes on start with a driver error | `DATABASE_URL` not wired to the database in Render |
